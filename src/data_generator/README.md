# response-generation pipeline (standalone)

Build a prompt set, serve a teacher model on every GPU, and generate assistant
responses at scale. Produces ShareGPT-style SFT / spec-decode training data.

The teacher model changes per run; the prompt set is **fixed** (deterministic
selection) so generations from different teachers stay comparable.

---

## Files

| file | purpose |
|---|---|
| `sample_nemotron.py` | the prompt builder for FRESH draws: download Nemotron-v2 (non-multilingual) → convert → capability-weighted 400K (deterministic md5) → dedup → length-cap → shuffle |
| `rebuild_prompts_from_manifest.py` | rebuild the ORIGINAL 220K prompt set from `manifests/nemotron_regen_220k_uuids.txt` (see the manifest section below) |
| `manifests/` | shipped uuid lists — pointers into the gated dataset, no content |
| `serve.sh` | launch N independent single-GPU vLLM servers (one per GPU/port) |
| `generate_responses.py` | the generator: fan requests across server endpoints, write JSONL |
| `stop.sh` | tear down all servers + generator, free GPUs |

---

## Quick start

```bash
# 0. One-time: build the unified project venv (vLLM 0.22.1 + everything). ~minutes.
#    Run from the repo root; see ../../pyproject.toml.
(cd ../.. && uv sync)

# 1a. Pipeline step 1 (the 220K set): rebuild the ORIGINAL prompt set from the shipped
#     uuid manifest (downloads ALL shards incl. multilingual, ~42GB once; needs HF_TOKEN).
HF_TOKEN=... ../../.venv/bin/python rebuild_prompts_from_manifest.py --output prompts_220k.jsonl

# 1b. Fresh draws (e.g. the 400K step-4 set): build prompts.jsonl with the sampler
#     (downloads ~3.6GB of non-ML shards on first run; cached after; needs HF_TOKEN).
HF_TOKEN=... ../../.venv/bin/python sample_nemotron.py --output prompts.jsonl \
    --max-prompt-tokens 14336 --tokenizer Qwen/Qwen3.5-4B --shuffle

# 2. Launch one vLLM server per GPU (loads ~3-4 min). MODEL is required; GPUS/PORTS per env.
MODEL=/path/to/teacher GPUS="2 3 4 7" PORTS="8124 8125 8126 8127" ./serve.sh

# 3. Wait for REAL readiness (a generation probe, not /health), then generate.
../../.venv/bin/python generate_responses.py \
    --input prompts.jsonl --output regen.jsonl --resume \
    --model <served-model-name> \
    --base-url http://localhost:8124/v1,http://localhost:8125/v1,http://localhost:8126/v1,http://localhost:8127/v1 \
    --concurrency 1200 --timeout 900 --max-tokens 16384 --keep-truncated --log-every 500

# 4. When done (or enough), tear everything down.
./stop.sh
```

Stop at a target (e.g. 120K): poll `wc -l regen.jsonl`, then `pkill -f generate_responses.py`.
Already-written rows are kept; a later `--resume` continues. The output is also reusable as
`sample_nemotron.py --exclude-ids-file` so the next sampling round never re-draws those prompts
(uuid-keyed outputs only — the historical 220K file is md5-of-text-keyed and would silently
exclude nothing; see the manifest section).

**Canonical output paths** — the rest of the pipeline reads these exact names, so
point `--output` at them (or move the file there afterwards):

| run | teacher | output path | consumed by |
|:--|:--|:--|:--|
| pipeline step 1 (220K) | BF16 `Qwen/Qwen3.5-4B` | `data/qwen3_5_nemotron_combined_regen.jsonl` (repo root `data/`) | `scripts/prepare_data.sh`, `scripts/train_drafter_pretrain.sh` |
| pipeline step 4 (400K) | packed QAD ckpt5000 | `src/data_generator/regen_ckpt5000.jsonl` | `scripts/train_drafter_finetune.sh`, `src/drafter_quant/build_calib.py` |

## Prompt selection (`sample_nemotron.py`)

Non-multilingual pool (multilingual* splits excluded): chat 627,720 / stem 355,000 /
math 239,467 / code 175,000 = **1,397,187**.

Default allocation is **capability-weighted** (~75% reasoning-dense skills), since chat is
over-represented for distilling a small reasoning model:

| split | selected | of unique pool |
|---|---:|---:|
| stem | 166,116 | 47% |
| math | 100,000 | 97% |
| code |  33,884 | 100% |
| chat | 100,000 | 18% |
| **total** | **400,000** | |

(Selection runs on **unique** user prompts — code is 80% duplicate so its ceiling is
33,884; the deficit tilts into stem. See the `DEFAULT_ALLOC` note in the script.)

Override with `--alloc 'stem=...,math=...,code=...,chat=...'`. Selection is `md5(uuid)`-lowest:
deterministic, reproducible, and a larger N is a superset of a smaller one. All rows are
single-turn `[system, user, assistant]` with an empty system, so the original assistant is
dropped (regenerated by the teacher) and a default system prompt is injected. The `reasoning`
field describes the *original* answer's think-trace, not the prompt, so it does not gate selection.

## The 220K manifest (`manifests/nemotron_regen_220k_uuids.txt`)

The pipeline's **step-1 corpus (the "220K set") predates `sample_nemotron.py`** and cannot
be re-drawn by it: it was selected with a different procedure, drew from the
**multilingual splits too** (`multilingual_{de,es,fr,it,ja}` ≈ 71% of it), and keyed rows
by `md5(user text)` instead of the dataset `uuid`. Because the generated corpus is a
derived artifact of the gated dataset, it must **not** be redistributed — so the repo
ships pointers instead: the `uuid` of every Nemotron-v2 row that fed the original
generation, recovered by content-hash matching every row of every split against the
original corpus.

- **219,602 uuids** — one per unique prompt (duplicate rows in the original corpus
  collapse to a single entry).
- `rebuild_prompts_from_manifest.py` turns the manifest back into `prompts_220k.jsonl`
  (schema-identical to `sample_nemotron.py` output, `id` = dataset uuid), scanning **all**
  data shards (~42 GiB download once). Feed it to `generate_responses.py` as usual.
- The historical corpus used `id = md5(user text)`; the rebuilt prompts use `id = uuid`.
  Row-level correspondence between the two keyings is a maintainer-side artifact
  (not shipped; regenerate it by hashing user text, or see the sweep outputs).

## Design decisions (learned the hard way — keep these)

1. **One independent server per GPU, NOT `--data-parallel-size N`.**
   vLLM DP on this model deadlocks under sustained load: all engines log
   `shm_broadcast: No available shared memory broadcast block found in 60 seconds`,
   `/health` stays 200 but generation hangs. Independent DP=1 servers have no
   cross-engine coordination, so they can't deadlock. The generator round-robins
   across them via a comma-separated `--base-url`.

2. **spec decode (dflash) is a throughput lever — but VERIFY output first (`SPEC` toggle).**
   For reasoning teachers it can cut decode time ~6× (decode-bound: 1 token/forward vs ~5
   accepted). HOWEVER, on the `qad_nemotron_regen` W4A16 checkpoints (e.g. ckpt5000) the
   dflash/EAGLE draft — which shares the target's *quantized* embed/lm_head — **corrupts
   output into repetition/garbage** (verified: SPEC=on garbled, SPEC=off clean). So
   `serve.sh` defaults `SPEC=off`. Only set `SPEC=on` after confirming a given checkpoint
   stays coherent with it (generate ~10 prompts, eyeball them).

3. **`--keep-truncated` is the biggest throughput lever (~6× kept-rows/s).**
   ~50% of responses hit the 16K `max_tokens` cap. Dropping them wastes the *most*
   GPU time (full 16K generated, then discarded). Truncated reasoning traces are
   valid teacher outputs for spec-decode training, so keep them. Use the default
   `--drop-truncated` only if you need fully-completed answers and can afford ~2× time.

4. **Match `--concurrency` to server capacity (~300 × n_servers).** Too high just
   deepens the server queue; tail requests wait past `--timeout` and fail. We saw
   timeouts vanish going 2048→1500 across 4 servers (queue depth ~310→~115/server)
   with no throughput loss. Servers saturate at ~250 running each.

5. **Launch the generator with `setsid`** if backgrounding it from a wrapper that
   cleans up its process group, otherwise it gets SIGKILLed silently:
   `setsid uv run python -u generate_responses.py ... > log 2>&1 < /dev/null & disown`.
   (vLLM servers survive plain `nohup`; the generator does not.)

6. **Do NOT pass a custom `http_client`** to `AsyncOpenAI` to raise the connection
   pool — it deadlocks the asyncio workers. With multiple round-robin endpoints you
   already get n × (SDK default 1000) connection capacity.

7. **`/health` lies during warmup.** In multi-engine mode it returns 200 before
   CUDA-graph capture finishes. Probe readiness with an actual `/v1/chat/completions`
   generation. A dead/unready endpoint won't crash the run, but its pinned workers
   silently fail ~1/N of items (re-run with `--resume` retries them) — so probe first.

## Prerequisite — CUTE patch (B300 / sm_103 only)

> Only needed on **B300 (sm_103)** with dflash spec decode. On H100-class (sm_90) GPUs
> this does not apply. Verify the spec-decode kernel runs on your arch with a 1-GPU smoke
> test before a large run.

dflash spec decode uses the CUTE sm100 FlashAttention kernel, whose arch guard
wrongly rejects B300 because `nvidia-cutlass-dsl 4.5.2` orders `sm_103a` above
`sm_110f`. Patch the assertion in
`.venv/lib/python3.12/site-packages/vllm/vllm_flash_attn/cute/flash_fwd_sm100.py`
(~line 162):

```python
self.arch = BaseDSL._get_dsl().get_arch_enum()
# local-patch: accept sm_103x (B300)
assert (self.arch >= Arch.sm_100 and self.arch <= Arch.sm_110f) \
    or (self.arch >= Arch.sm_103 and self.arch <= Arch.sm_103f), "Only SM 10.x and 11.x are supported"
```

Without it, generation crashes with `AssertionError: Only SM 10.x and 11.x are supported`.
Re-apply after any venv reinstall.

## generate_responses.py — key flags

| flag | default | notes |
|---|---|---|
| `--input` / `--output` | — | prompt JSONL / output JSONL |
| `--base-url` | env `VLLM_BASE_URL` | **comma-separated** list → round-robin across servers |
| `--model` | — | served model name |
| `--resume` / `--no-resume` | resume on | skips `id`s already in `--output` (restart-safe) |
| `--concurrency` | 128 | in-flight requests (set ~300 × n_servers) |
| `--max-tokens` | 2048 | use 16384 here |
| `--keep-truncated` / `--drop-truncated` | drop | **keep** for max throughput / spec-decode data |
| `--timeout` | 600 | per-request seconds; 900 gives margin |
| `--thinking` | auto | `on`/`off` forces `enable_thinking` via chat_template_kwargs |
| `--temperature/--top-p/--top-k` | 0.7 / 0.8 / 20 | sampling |
| `--priority-categories` | — | comma list to generate certain categories first |

## Output schema (one JSON object per line)

```json
{
  "id": "<id from prompt>",
  "category": "chat|stem|math|code",
  "conversations": [
    {"role": "system",    "content": "..."},
    {"role": "user",      "content": "..."},
    {"role": "assistant", "content": "...reasoning... </think>\n\nanswer"}
  ],
  "gen_model": "<served model name>",
  "finish_reason": "stop|length"     // length = hit max_tokens (truncated)
}
```

**Format note:** when the chat template emits the opening `<think>\n` into the prompt side,
the assistant `content` starts *inside* the reasoning trace; `generate_responses.py` re-attaches
the opening `<think>\n` so the stored message is self-contained. If your training re-applies the
same chat template, it stays consistent.
